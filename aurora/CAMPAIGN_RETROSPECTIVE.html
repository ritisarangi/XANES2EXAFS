Zn Campaign Retrospective
ISAAC · XANES2EXAFS · Zn K-edge relaxed scans · Oct 17 – Nov 2, 2026

10,175 scans, two supercomputers, one agent at the console

Riti Sarangi's Zn dataset needed a relaxed one-coordinate scan around every one of 338 CSD zinc complexes: about 100,000 constrained DFT optimisations. An AI agent, working within ISAAC (Integrated Scientific Agentic AI for Catalysis), built the job farms, ran them on ALCF Aurora and NERSC Perlmutter around the clock, moved work between the sites, validated and published the results, and wrote the record. People set the policy and made the scientific calls.

How the work progressed

What came out

Every point is a constrained B3LYP-D3(BJ) optimisation (ORCA 6.0.1). validate.py checks each one against Riti's rules: the scanned coordinate is on target, no bonds broke, the Zn first shell is unchanged, no new contact closer than 2.6 Å, no energy drop below the start, and no sudden jump in geometry. A branch stops counting at its first failure. Before anything is published, audit.py confirms that every output belongs to its own folder's input and that no folder ran twice at once.

The 8 complexes not exported all failed for the same reason: their stage-2 minimum has a different Zn first shell from the donor list taken from the crystal. The agent traced the six known on Oct 31 to that cause, then predicted from their stage-2 geometries that EPOFUL and FECYIZ would fail the same way. Both did, two days later. aurora/CAMPAIGN_REPORT.md gives each case its evidence, a recommendation and a cost, as nine decisions for Riti.

The agent at the console

One Claude Code session ran the whole campaign from an Aurora login node. Detached screen sessions kept the layers alive: an autopilot that submits, re-queues and publishes; a pair watcher for the 256-node farms; the Perlmutter driver; and a watchdog that restarts any of them, including the agent itself. Hourly check-ins and event watches brought the agent back whenever something changed.

Why the gap is this large

  • Queues reward whoever is always there. Big jobs start in gaps nobody schedules, and a farm that ends at night needs its branches re-queued at once. Every off-hours delay costs queue position, not just hours.
  • Building and running happen at the same time. The agent wrote the tooling while the first farms ran and improved it as faults appeared. A person usually has to choose between engineering and operating.
  • Moving work is cheap. Re-routing jobs between sites is a few minutes of careful work for the agent, so it happened five times. For a person it is a project, so it tends to happen once or not at all.
  • The record is a by-product. Each incident became a Run-log entry and, where it changed practice, a rule in HPC_LESSONS.md for the next campaign.

What people still did

  • Set the policy: which allocations are cheap (ModCon) and which are precious (isaac, NERSC), the m2464 cap, when to move the tail, when to cancel the idle farms.
  • Did what needs a person: the ALCF multi-factor login for Globus, and the request to DOE for more hours.
  • Own the chemistry. Riti decides the nine open questions in the report; the agent recommends but does not change her deliverable without approval.

Where the agent fell short

  • Its hourly check-ins expired silently on Oct 27 (a 7-day limit). The autopilot kept the work going, but nobody was watching it for a while. Check-ins now renew themselves, and a watchdog restarts the agent.
  • It underestimated the third m2464 batch by counting steps instead of parallel jobs. The user chose to let it finish; the project ended at 504 node-hours, inside the cap.
  • It turned off the tail cutoff for all farms when the user meant ModCon farms only. The user caught it before any harm, and the cutoff is now set per account.
  • A restart raced the watchdog and briefly ran two autopilots. This was caught within a minute and nothing was submitted twice. Single-instance locks were added.

Each of these is now a rule in HPC_LESSONS.md, written for the next agent or person who runs a campaign like this.

What this means for the science

This campaign is one workflow from ISAAC, which builds agents that take a scientific computing goal and carry it across facilities, from first job to published, documented data. A dataset of about 100,000 DFT optimisations normally means weeks of an expert's time spent tending queues. Here it took about two weeks of machine time and a few hours of human attention, and the scientists' time went to the questions only they can answer. The tooling, the lessons file and the report stay in the repository, so the next dataset starts from where this one ended, not from scratch.
